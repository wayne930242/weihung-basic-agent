# Rotating a long-lived session

A long-lived main (a standing session, or a coordinator that runs for days) rotates its session only on a concrete problem: the session repeatedly stalls (pi stops answering keys for seconds) because of its own long history, or compaction has visibly lost context the work needs. A milestone, a long history, or a doctor nudge alone is no reason, because a new session starts without the prompt cache.
To rotate, write `scratch/handoff-<name>.md` with the goal and the anchor command and result. `boss_handover` (pi-straw-boss 0.89.0 or newer) carries the todo list itself: it writes the list, ids, anchors, and evidence included, to `scratch/handoff-<name>.todos.json`, and the successor restores it with `todo` `import` (pi-todo-ledger 0.2.0 or newer). With an older pair, the handoff also lists the status of each open todo.
List the monitors and loops to recreate, the replies you owe and to whom, and the branches and worktrees in flight. Quote the user's last instructions verbatim.
Then open your successor yourself with `boss_handover {handoff: "scratch/handoff-<name>.md", reason: <the concrete problem>}`: it opens a new tab in your workspace with a pi under your name and kind whose first prompt is the handoff. Only where `boss_handover` is missing (pi-straw-boss before 0.82.0), open it yourself with `herdr tab create` and start pi there on the handoff; never ask the user to run `/new`. The new session reads the handoff, restates the check on an `Anchor:` line, imports the todo file its first prompt names (or, without one, restores the open todos from the handoff), recreates the monitors and loops, and keeps the kind it was opened with (it runs `boss_duty` only when the handoff names a different kind). Then it tells the old session by intercom (the handoff names its id) that it took over. The old main then gives up its role, because towers route standing work by kind and name, and two standing mains of one name both get it: it runs `boss_duty coordinator` (when it was standing or integrator), renames itself with `boss_rename` to `old <name> (handed over to <new id>)`, stops its monitors and loops, clears its board, and waits for its workspace's tower to close it: `boss_handover` tells the tower, which closes the old main once its successor is live, whoever opened it. With no tower in the workspace, the user closes it. Never run `/new`, kill a process, or stop running work to rotate.
